The 87 research/repro tickets are the real cost center. Each individual reply isn't much slower than a routine ticket (7.7h vs 6.1h) — the pain is rounds: users get bounced back and forth while we investigate. A ticket in this bucket waits 4× longer in total than a straightforward one. Known-problem tickets, by contrast, resolve fastest per-reply (4.9h) because the answer is already templated — the fix belongs to engineering, not support capacity.

Methodology & glossary

Complexity segments: Straightforward = never entered Hold status. Research/repro = entered Hold at least once, not linked to a tracked Problem. Known problem = ticket type Incident, linked to a Problem ticket.

Total wait / between-reply gap: computed from actual public comment timestamps (customer comment → next public agent reply), not ticket status — avoids the pending/hold/bump-macro distortion that inflated calendar-time metrics in the prior report design.

Confirmed bug rate: % of a theme's tickets with a GitHub issue link (zd-gh tag) attached.

Ticket subjects and content are aggregated/categorized only — no raw customer text or PII in this report. This is a prototype for internal design review; not published to GitHub Pages.
